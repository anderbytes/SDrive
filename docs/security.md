# Security and limitations

## Trust boundaries

- The interface loads local files and has a CSP. It has no telemetry, CDN or remote interface code.
- The Wails bridge exposes specific operations. The rclone RC API is not exposed directly to the interface; it listens only on loopback, with a random password per run and no open CORS.
- RC API access grants the privileges of the process owner. Do not share the endpoint or its credentials.
- Secrets persist in encrypted rclone configuration. The random key is protected by DPAPI. Only helper process environments receive the required keys.
- DPAPI and directory permissions do not protect against malware running as the same user, administrators, memory capture or Windows compromise.
- The cache contains file content without additional SDrive encryption. Use system disk protection for sensitive data.

Application PIN protection, idle disconnect, administrative recovery, file-access queries and shared-editing limits are described in [application access and mounted file operations](access-and-file-operations.md). A management lock does not revoke access to mounted files.

## Transport and providers

The connection-type selector describes **traffic encryption**, separately from encryption of stored files or the local configuration. Required protection covers HTTPS cloud services and SSH-based SFTP. WebDAV/Nextcloud/ownCloud, FTP/FTPS, S3, Azure Blob Storage, MEGA and SMB offer optional transport protection; no current profile lacks an encryption-capable transport. Optional does not mean every engine option is exposed by SDrive. MEGA uses HTTP for transfers by default while encrypting file content independently; its `use_https` option is not currently exposed in the interface.

Connected drives show encrypted, unencrypted or unverifiable transport, the protocol, the source of the assessment and the check time. Mandatory protocols are identified from an established connection and its backend; configurable transports use the worker's actual configuration, including the currently selected WebDAV URL, rather than the permission to allow insecure traffic. These assessments are not packet captures or proof about every transfer, redirect or external proxy. Configurations containing unhandled engine overrides remain unverifiable.

SMB additionally queries the negotiated session and share flags through a read-only engine extension. Either session-wide or share-specific encryption counts; signing alone does not. This is a sample from a live pooled connection for the selected share, not a guarantee about every concurrent connection. A server-root mount spanning multiple shares is unverifiable. Missing extensions, malformed responses and timeouts never imply encryption. Checks share the snapshot deadline, have a 500 ms limit, and are reused for at most 30 seconds; lifecycle changes invalidate them. Disconnected drives carry no current protection claim.

TLS certificates are verified. HTTP and plain FTP require explicit selection per connection. For SFTP, the public key is obtained without authentication; the user verifies its fingerprint and accepts the key before sending credentials. Key changes are not accepted automatically. This initial verification helps avoid trusting a malicious intermediary.

OAuth opens the selected external browser using an application registered by the user. Client ID and Client Secret for the supported registration flows are checked before authorization, including non-guided bridge calls. Saved user identities are preserved during renewal; changing the Client ID requires its matching secret. Neither SDrive nor rclone shared clients are used as fallback. Provider approval, administrator consent and Testing-mode renewal remain the user's responsibility. See [OAuth setup](oauth-setup.md).

Persistent tokens/secrets remain in DPAPI-backed encrypted configuration; session-only connections use an in-memory worker. No Client Secret is embedded in the application. Known additional steps have English messages and Portuguese translations; unknown steps stop the wizard. Browser URLs are obtained only from the authenticated engine, constrained to its loopback callback and never stored in diagnostics. Private mode requires a supported installed browser and is never silently ignored.

[Connection networking](connectivity.md) documents per-connection processes, supported HTTP bandwidth/proxy routing, session-only recovery and read-only WebDAV identity verification. The legacy root config and per-remote configurations have separate writers. The local authenticated RPC remains direct. Original remote names/cache namespaces remain stable during legacy import and pending recovery.

## Writes and recovery

The VFS cache is persistent. [Cache location and mount runtime](mount-runtime.md) describes the independent location binding, clean-only transitions, directory refresh and owner ACLs for local mounts. A potentially interrupted session is recorded before mounting. Pending files are checked through the rclone API and the local metadata `Dirty` field, including open files that have not entered the upload queue. `Dirty` must be an explicit JSON boolean: absent/null fields, invalid types, malformed metadata, links, unexpected cache roots and backing files without metadata never establish a clean cache. Critical `vfs/stats` fields must be present and correctly typed, with nonnegative counters and overflow-safe upload totals. These readers follow the pinned [rclone 1.75.2 cache statistics](https://github.com/rclone/rclone/blob/v1.75.2/vfs/vfscache/cache.go) and [metadata schema](https://github.com/rclone/rclone/blob/v1.75.2/vfs/vfscache/item.go); revalidate them on engine upgrades.

A snapshot carries `pending: null` when the complete pending count cannot be checked. The interface shows unknown status and a partial summary instead of interpreting a failed check as zero. Queued/active uploads and cache errors are separate: `erroredFiles` describes cache errors, not a count of failed uploads. Pending totals use the maximum of the durable dirty count, queued plus active uploads, and cache-error count; these sets may overlap. They are a conservative status indicator rather than an exact count of unique files across every source. There is no inferred completion percentage or per-connection transfer speed.

Display inspections, including failures, are reused for up to 30 seconds and show their sampling time. They are invalidated when connection lifecycle operations change the relevant state; overlapping inspections do not publish incomplete or invalidated results. Live engine statistics are still requested on every snapshot. Display samples never authorize disconnect or safe exit: disconnect checks fresh engine statistics and durable metadata, unmounts, then performs a new durable inspection before clearing the recovery flag. Safe exit also checks disconnected saved connections. Uncertainty keeps recovery protected and blocks a safe-exit declaration.

Inspection reads directories in batches of 128 entries, limits each metadata file to 8 MiB, and checks cancellation between entries and reads. Snapshot inspections share a two-second deadline; disconnect shares a 35-second deadline across its drain, unmount and final inspection. Incomplete/oversized inspections remain unknown; unusually large legitimate metadata may require a compatible reader or manual recovery. Local operating-system calls already in progress cannot be forcibly interrupted by these context checks.

Cache figures distinguish the configured target per connection, approximate cache use, free bytes available on the cache disk and the logical sizes of whole local dirty files. Mounted use comes from rclone `bytesUsed`; disconnected use is sampled with Windows allocated-size information so sparse files are not counted at their entire logical size. These are approximate measures, exclude filesystem overhead, and are not the bytes remaining to upload. Missing measurements appear as unavailable, independently of pending-state safety. Pending sizes require all dirty backing files to be measurable. Pending data remain preserved even above the configured target; there is no cache-delete action in this interface.

Before disconnecting, close files in other applications. There is no distributed transaction between an editor, Windows, cache and provider. Forced shutdown, disk failure or data an editor has not submitted to the system can cause losses SDrive cannot recover.

After an interruption, keep the cache and original destination. Changing folders/servers or removing connections is blocked while recovery is pending. Renewing credentials must not change the account that owns the files.

Before mounting, SDrive binds cache to the destination options and identifiers available in configuration, including the library/drive and remote folder. OAuth renewal that selects another library does not authorize sending old cache there. This binding does not prove account identity for providers that do not persist their own account identifiers: always renew with the same account.

Recovery renewal also checks that binding before reporting setup success. A mismatch preserves the original recovery flag and hash and blocks completion and mounting. Renewal updates the existing encrypted remote; cancellation does not roll back credentials already written by the provider and never deletes that recovery remote. Sign in again with the original account/library. No token, password, key-file path or credential rotation becomes account identity. Existing hashes are unchanged; the per-profile limits are recorded in [provider validation](provider-validation.md#recovery-identity-limits).

FTP renewal restores the saved explicit FTPS, implicit FTPS or plain FTP mode. Missing TLS flags mean false, matching rclone defaults; contradictory or invalid flags stop renewal. Both flags are written explicitly to prevent stale transport settings. Recovery cannot change transport, and plain FTP requires fresh explicit consent. Failed access-detail loading blocks submission rather than reverting to the default transport.

Setup accepts a complete, typed rclone question/completion response and verifies the exact saved remote's backend and required configuration before proceeding. This verifies configuration, not read/write permissions: folder selection still performs a read-only access check. Provider failures expose fixed messages for recognized network, credential and permission signals, with a generic fallback for ambiguous responses. Authentication failures of the local RPC endpoint are reported as local engine failures. Raw provider error text is inspected only in memory and is not included in application errors.

Password, token, secret, MFA, OTP, 2FA and verification questions are masked even without provider password hints, including numeric verification codes. Sensitive defaults and examples are removed before reaching the interface. Show/hide controls reveal only user-entered values in the current form, start hidden and reset when a step is reopened or a question is submitted. Neither revealed state nor credentials are stored in browser storage.

The helper process belongs to a Windows Job Object, preventing it from running unsupervised after SDrive exits. After an unexpected exit, persistent files remain for recovery on the next launch.

## Local settings recovery

`settings.json` uses format version 5. Versions 1, 2, 3 and 4 remain readable. The supported historical format has no version and may omit the language, which defaults to English. All supported formats require a connections array and a settings object containing an explicit startup preference and cache limit. Empty objects, null values, incomplete structures and unsupported versions cannot authorize credential cleanup. Reading an old file does not migrate it; the next successful save writes version 5 and binds the authoritative cache location. An incompatible version requires a compatible application, rather than restoration by an older application.

Every settings save first preserves the previous valid file as `settings.backup.json`, then atomically replaces the primary file. The first save also creates the initial backup. A failed backup prevents replacement; an invalid existing primary is never overwritten by an ordinary save. Both files contain connection metadata, not encrypted credentials or cached file contents. They are not a backup of the whole profile. An intentional connection removal or credential replacement can make an older connection's credentials unavailable.

If local settings are damaged or an established profile's settings disappear, SDrive opens its recovery interface without starting the engine or creating keys. Restoration requires explicit confirmation and a compatible, validated local backup. The original file is retained as a unique `settings-damaged-*.json` archive. If preservation or replacement fails, restoration fails and the original data remain. Missing or unreadable backups require manual recovery; do not reset the profile or delete its files to dismiss the error.

Before restoration, SDrive writes `settings.recovery`. This durable protection suspends automatic mounting and orphan cleanup across restarts. Restored connections with existing cache require recovery at their saved destination; missing destination evidence blocks mounting. Recover and disconnect those drives, then choose **Verify recovery**. Verification requires all generated remotes and cache directories to belong to the restored connections, all required credentials to exist, and no active or pending recovery. Unknown credentials/cache remain preserved for manual recovery; they are never deleted to make verification pass. Editing/removing connections and creating replacement connections remain blocked during this protection, apart from renewing credentials for a connection already marked for recovery.

For manual recovery, exit without starting new writes and preserve the entire SDrive data directory, including the damaged archive, backup, `settings.recovery`, encrypted configuration, key and both cache trees. Reconstruct missing connection metadata only from trusted records of the original account and destination, using compatible software or maintainer assistance. Do not guess a destination, remove the recovery marker manually, or share the profile in an issue. Reopen SDrive and use **Verify recovery** once all data are accounted for. A lost DPAPI key cannot be reconstructed from the settings backup.

Restoration does not apply its Windows startup preference. Save preferences explicitly to reconcile it. A failed settings save restores the previous preference in memory and attempts startup rollback; failure of that rollback is reported together with the original error. Startup disagreement is also checked when reopening. Unit tests inject startup operations and never modify the real startup entry.

Keys and settings use synced temporary files followed by atomic promotion. Key creation never replaces an existing key; concurrent creation reuses the winning key. Missing keys beside existing encrypted configuration, unreadable configuration and empty/corrupt keys cause recovery errors rather than regeneration. Orphan-cleanup failures are separate maintenance warnings and can be retried without preventing use of saved connections. Cleanup preserves current/backup references and existing cache; unreadable evidence suspends deletion.

## Local diagnostics

SDrive automatically collects minimal local events after securing and exclusively locking the profile. Each event accepts only a timestamp, an allowlisted stage, result and category, and an optional numeric engine exit code. Raw errors, log messages, RPC inputs/responses, command arguments and environment values never enter the collector. Engine stderr is inspected in memory to classify recognized signals and discover its local API; URLs, paths, tokens, connection identifiers/names and file contents are not stored in diagnostics. Unrecognized failures use `unknown`. The last observed signal is context, not proof of the cause of an engine exit.

`diagnostics.jsonl` and `diagnostics.previous.jsonl` inherit the profile's current-user/SYSTEM directory protection. Each file is limited to 128 KiB; rotation removes the older diagnostic file. The collector keeps only the latest 256 valid events in memory, including validated history from earlier runs. Retention is capacity based, without an age limit. Reads are bounded; corrupt, oversized or unrecognized history is discarded from the report. Only these two diagnostic files are managed by rotation. Credentials, settings and cache are never diagnostic cleanup targets.

Recording does not wait for disk I/O: a 64-event queue feeds a background writer. If the queue is full, current events remain in bounded memory and the report counts records dropped from persistence. Storage failures and invalid history are reported without exposing operating-system error text. They do not fail drive operations, permit an unsafe exit or disable recovery protection. Shutdown waits up to 500 ms for the writer. Recent records can be lost after interruption, storage failure, queue overflow or that shutdown deadline; this is a troubleshooting aid, not an audit trail or recovery journal. Repeated identical engine log signals and RPC failure categories are suppressed until a different category occurs or the engine restarts.

**About SDrive → View diagnostics** generates a plain-text report from validated numeric component versions, aggregate state and allowlisted events. It works without a running engine or readable settings; unavailable versions are explicit. Opening the report does not copy, save or transmit it. **Copy report** copies exactly the displayed preview only after your action. Review it before sharing, and remember that clipboard contents are available to other applications and may be synchronized by your Windows clipboard settings. There is no automatic upload, support submission, analytics or telemetry.

For safe manual updates, repair and incompatible settings, follow the [user instructions](../README.md#update-repair-and-collect-diagnostics). Preserve the full profile privately if manual recovery is needed; share the sanitized report rather than the profile, raw stderr or configuration dumps. Installer rollback/transactionality and compatible-version support still require their own release validation.

## Distribution and reporting

Tool versions and files are pinned; tool files use SHA-256 and Go sources use module/SumDB checksums. Checksums do not prove that a binary exactly reproduces its source. Local builds do not have a publisher's digital signature.

The online installer includes SDrive and rclone and downloads WinFsp/WebView2 only when needed. The offline alternative includes all components. Downloads accept only HTTPS and files defined in the embedded manifest, with size and time limits. Partial files are never executed. Both variants verify SHA-256, Authenticode signature and publisher before executing each component; the file remains open without write/delete sharing until execution finishes. Signature trust uses local Windows certificates without mandatory online revocation checks.

Only the official WinFsp MSI requests elevation. SDrive and downloads run as the regular user. Uninstalling SDrive does not remove shared components. Installer-requested restarts are communicated, never forced.

The official rclone 1.75.2 binary uses Go 1.26.9 and was reported by `govulncheck` as affected by [GO-2026-6809](https://pkg.go.dev/vuln/GO-2026-6809), concerning compromised intermediate certificates. SDrive therefore rebuilds unmodified official sources with Go 1.26.10, which includes the fix.

There is a known discrepancy in OpenPGP analysis: `govulncheck -mode=binary` still reports [GO-2026-5932](https://pkg.go.dev/vuln/GO-2026-5932), while rclone source analysis with `-tags cmount` reports zero reachable vulnerabilities. The effective import tree does not include `golang.org/x/crypto/openpgp`; it uses the maintained `github.com/ProtonMail/go-crypto/openpgp` fork recommended by the advisory. The inference is a binary-analysis alert unconfirmed by source analysis; this is not proof of a general absence of vulnerabilities. Reassess when updating tools or dependencies.

To reproduce, use `govulncheck` v1.9.0 on SDrive and at the rclone 1.75.2 source root with `-tags cmount .`, as well as binary analysis. Initial SDrive and rebuilt rclone source analyses reported zero reachable vulnerabilities; binary analysis still reports the OpenPGP alert described above.

Never submit configuration dumps, tokens, keys, passwords, SAS URLs, cache directories or user files in issues. For suspected vulnerabilities, use a private repository advisory when available; in public issues, report only that a problem exists, without sensitive data or exploitation details.


## Concurrent operations and ownership

SDrive holds an exclusive `instance.lock` file handle inside its actual data directory until the engine has stopped. Windows file sharing enforces ownership across processes and login sessions, including file aliases. The file remains after exit; its existence is not a stale lock. Startup, installation and uninstallation check ownership, while the legacy session mutex remains available for older installer checks. The installer probe does not reserve the entire update interval; preventing launch throughout replacement remains separate update-lock work.

A second launch cannot load settings or start another engine while that profile is owned. In the same Windows session it sends a bounded, activation-only message to the existing Wails receiver, identified by the current user and canonical profile directory. No arguments, paths or credentials are forwarded. Activation grants foreground permission only to the receiver's process. A profile owned in another session remains locked and receives an explanatory activation failure; independent profiles retain separate ownership.

`window.json` contains only normal window bounds and maximization state. It is written atomically and is independent of connection settings and recovery backups. Missing or invalid geometry uses defaults; restored bounds are clamped to current monitor work areas. Failure to save geometry warns once and does not affect drive operations or safe exit. About reads component versions locally and requests only `core/version` from the captured engine; unavailable versions remain explicit.

When hidden or minimized, native status sampling continues every 15 seconds and visual snapshot polling stops. New problems reveal the window once per changed problem, including recovery and unknown pending status. Active mounts' normal recovery markers and ordinary pending uploads are not failures. Tray connection actions use the same service validation and durable disconnect/exit checks as the interface; cached display status never authorizes a safe exit.

Provider calls for setup, folder selection, connection inspection and mounting run outside the service mutex using a captured engine. State-changing operations reserve their connection or setup, then revalidate before applying results. A canceled or superseded setup cannot commit a late folder confirmation. Frontend snapshots discard responses and errors superseded by a newer request or an action, and responses arriving after unmount.

Configuration writes use rclone asynchronous jobs. Cancel requests server-side job cancellation and waits for a confirmed terminal status before deleting the temporary remote. A lost start response is recovered by its unique job group, without repeating the write. If cancellation cannot be confirmed within five seconds, Cancel returns an error and preserves the reserved setup; retry Cancel when the engine responds. Unknown or expired job status never authorizes credential deletion. If the engine permanently loses the job record, setup remains reserved until engine termination; do not delete credentials or cache manually to bypass this protection. In-place recovery and already committed remotes are preserved.

Snapshots reconcile rclone's mount list with the saved remote, drive letter and in-memory state. Unexpected unmounts preserve recovery markers; conflicting destinations and discrepancies with Windows drive availability are reported. A matching engine mount with an unavailable Windows letter stays eligible for Disconnect. Malformed or unavailable mount lists produce unknown pending status rather than a clean-cache claim. These checks cannot prove provider account identity or certify native mounting without the corresponding real-environment tests.
